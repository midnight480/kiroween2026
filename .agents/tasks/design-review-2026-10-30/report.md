## 1. 総評（サマリ）

この設計メモは、ハッカソン応募作品の企画書として**完成度が高く、特に「技術的に成立するか」の検証が実機で裏取りされている**点が際立つ。GnuCOBOL 3.2.0 での構文チェック・実行確認（§16.2〜16.3）、予約語衝突の確認（§16.5）、CloudFormation `AWS::DynamoDB::GlobalTable` の MRSC 表現確認（§16.4）は、企画段階のドキュメントとしては異例に堅い。README の方針（「CloudFormation にコンパイルするフレームワーク」「10/30 までは企画・設計のみ」）とも矛盾しない。サンプル `.cbl`（verify/samples/）は §5 のコードブロックと**完全一致**しており、ドキュメントと検証物の対応が取れている。

一方で、**企画書としては十分だが「実装の設計書」としては未確定の論点が多く残る**。特に、(a) トランスパイルの中核であるセマンティクス（COBOL の構造から CFN プロパティへの写像ルール）が規約の列挙に留まり仕様化されていない、(b) リージョン情報の取得元が二重定義になりうる内部矛盾がある、(c) IAM・Lambda サンプルに CFN として必須のプロパティが欠けており「サンプルがそのまま有効な CFN になるのか」が曖昧、という 3 点が実装着手前に効いてくる。

結論として、**企画・審査対策の文書としてはこのまま通用するが、W1 でスペック化する前に「トランスパイラの意味論」を 1 段階詳細化しておくべき**。以下、設問順に評価し、最後に優先度付きの改善提案を示す。

## 2. 設問への回答（評価）

### Q1. 問題・ゴール・スコープ/非ゴールの明確さ → おおむね明確（◎に近い○）

- **問題設定**は §1〜§2 で明快。「COBOL はクラウド/IaC 言語としては存在しない」→「COBOL を IaC 言語として復活させる」というフレーミングは一貫している。Resurrection 部門への適合理由（§2）も具体的。
- **スコープ**は §11 で MVP / ストレッチに分離され、必達リソース（S3 / IAM Role・ManagedPolicy / Lambda / DynamoDB 単一＋MRSC）が列挙されている。§12 の 5 週スケジュールとも対応。
- **非ゴール**は明示項が散在している（`Pro*COBOL`/`EXEC SQL` 不使用=§4.1、jsii に COBOL を足すものではない=§1/§6、Skeleton Crew 部門は対象外=§3）。ただし「非ゴール」という独立した節がなく、読み手が拾い集める必要がある。
- 弱点: **審査基準・提出要件が丸ごと TBD**（§0 の表、§14）。これは外部要因でやむを得ないが、「ゴールの定義が審査基準に依存する」ため、W1 改訂待ちの前提が設計全体に乗っている点は明記のとおりリスク（§13 最上段）。

### Q2. アーキテクチャの技術的妥当性・実現可能性 → 妥当だが中核が未仕様（○）

- **パイプライン（§6）** は Card Reader → Lexer/Parser → Semantic → IR → Emitter → Reporter/Deployer という素直な構成で、静的トランスパイル方式の選択は COBOL の性質（`01`=リソース、`VALUE`=プロパティが静的に読める）に照らして妥当。CDK の jsii との区別（§1/§6 冒頭ノート）も論理的に正しく、審査対策として有効。
- **実装言語 TypeScript＋Chevrotain 候補**、`npx` 配布、ブラウザ内コンパイル流用（§8）という選定理由は一貫している。
- **ギャップ（最重要）**: `[4] IR` は `{logicalId, type, properties}` とあるが、**COBOL の各構文要素が CFN のどのプロパティにどう写像されるかの「意味論の表」が存在しない**。たとえば:
  - 5.1 の `VERSIONING-FLAG VALUE "Y"` / `88 VERSIONING-ON` → `VersioningConfiguration.Status: Enabled` への変換ルールが未定義。
  - 5.1 の `BLOCK-PUBLIC "Y"` → `PublicAccessBlockConfiguration`（4 フラグ）への展開ルールが未定義。補足に「省略時も既定で全ブロック」とあるが、どの CFN プロパティに落ちるかは書かれていない。
  - 5.2 の `TRUST-SERVICE "lambda.amazonaws.com"` → IAM Role の `AssumeRolePolicyDocument`（JSON 構造）への生成ルール、`MANAGED-POLICY "AWS-MANAGED:..."` 接頭辞 → `ManagedPolicyArns` の ARN 補完ルールが未定義。
  - §4.4 の `"REF:LOGS-BUCKET"` → `Ref`、`"GETATT:FN-ROLE.ARN"` → `Fn::GetAtt` は示されているが、**参照先の解決スコープ**（同一ファイル内の `01` 名のみか、クロスファイルか）は未記述。
  これらは「規約で表す（§4.1）」という方針に委ねられているが、**規約＝写像仕様そのものなので、列挙されていないと [3]Semantic / [5]Emitter が書けない**。W1 のスペック化（§10 の Spec②）の直前に、最低限 MVP の 4 リソースぶんの写像表が要る。
- **Emitter の自動生成案（§5「CFN リソーススキーマから表を自動生成する案 ⚠️」）** は野心的だが未確定。MVP では手書きマッピング表に倒すのが現実的で、ドキュメントもその旨を決めておくべき（現状は「案」で浮いている）。

### Q3. README・COBOL サンプルとの整合 → 高い（◎）、ただしサンプルの CFN 妥当性は別問題

- README の記述（「純粋な固定形式 COBOL で AWS の IaC を書き、CloudFormation にコンパイル」「10/30 まで企画・設計のみ」）と DESIGN のステータス・方針は完全に整合。
- `verify/samples/*.cbl` は §5.1〜5.4 のコードブロックと**逐語一致**。`deploy.cbl`（`PROGRAM-ID. DEPLOY.` が `DISPLAY` して `GOBACK`）は §16.3 の実行実証で使われたダミーサブプログラムと一致。ドキュメントの「✅ 検証済み」記述は検証物と対応が取れている。
- サンプルが **GnuCOBOL の固定形式構文チェックを通る**（§16.2）のは確認記録として妥当。`CALL "DEPLOY"` が実行時解決の標準 CALL 文であること、`ASSIGN TO "DYNAMODB-MRSC"` が単なる外部名リテラルとして通ることも、COBOL の言語仕様上正しい挙動で、記述に無理がない。
- ただし **「構文として有効な COBOL」と「意味のある CFN に変換できる COBOL」は別**。たとえば `52-lambda.cbl` の `FN-ORDERS`（`AWS::Lambda::Function`）には **`Code`（S3 の場所 or インライン）に相当する項目が無い**。CFN の Lambda::Function は `Code` と `Role` が必須なので、このサンプルをそのまま emit すると**デプロイ不能なテンプレートになる**。設計上「Code をどう表すか」（ZIP の S3 配置？ 別リソース？）が §5 にも §4 にも無い。同様に `AWS::IAM::ManagedPolicy`（5.3）は `PolicyDocument` が必須だが、`OCCURS` の STMT をどう `Statement[]` に組むかの変換は補足レベルの言及に留まる。→ **サンプルは「COBOL として有効」の実証には足るが、「有効な CFN を生む」実証には不足**。この境界を文書で明示すべき。

### Q4. 抜けている考慮（エラー処理・エッジ・セキュリティ・テスト・運用・スケール）

- **エラー処理**: 入力側（桁ずれ・小文字・PIC 長超過・未定義参照・`DBLINK`）は §7/§9.1 で厚く、行・桁つきエラーの方針も良い。一方 **出力/デプロイ側のエラー処理が薄い**。CFN デプロイ失敗時は §7 の「ABEND S0C7 風ダンプ」演出だけが書かれ、ChangeSet 失敗・ロールバック・スタック既存時の扱い・認証失敗のハンドリングが未設計。§4.6 の `deploy` は `CreateChangeSet → ExecuteChangeSet → DescribeStackEvents`（§6[6]）だが、各段の失敗分岐が無い。
- **エッジケース**: 継続行（7桁目 `-`）、ピリオドの扱い、`MOVE` が複数回同一項目に当たる場合、`CALL` が複数/未記載（§4.6 で主段落の最初の CALL を既定、と一応カバー）、`OCCURS` の添字が範囲外、`REF:` の循環参照 — これらの一部は §13 のリスク「パーサが沼る」で認識されているが、**どこまでを MVP サブセットとして受理し、どこから明示エラーにするかの線引きが未確定**。
- **セキュリティ**: 方針は良い（§5 補足の「Security by default = 全ブロック」、§4.5 の `*` ワイルドカード警告、§9.5 の cfn-guard/checkov）。ただし MVP 必達でなくストレッチ寄り。デモ UI の「認証付きバックエンド＋デモ専用アカウント＋Budgets」（§8/§13）は言及があるが、**ブラウザ内コンパイル→実デプロイの認証経路**（クレデンシャルの持たせ方）が未設計で、ここは漏洩リスクがあるため早めに決めるべき。
- **テスト/検証**: §9 は本ドキュメントの中で最も堅い。Vitest 単体、ゴールデンテスト（正規化 deep equal、`UPDATE_GOLDEN=1` ガード）、GnuCOBOL 構文 CI、cfn-lint、cobol-check（Emeritus のため任意）まで整理済み。良い。唯一、**ゴールデンの「期待 CFN」を誰がどう最初に作るか**（手書き起こしか、初回生成を人手レビューして確定か）の運用が未記述。
- **運用**: デモ専用アカウント＋Budgets＋CI で必ず DESTROY（§13）は妥当。ただし `destroy` の確認プロンプト（§4.6）と CI の自動 DESTROY（§9.6 nightly）の関係（CI では非対話で回す必要）が未整理。
- **スケーラビリティ**: 作品の性質上ランタイムのスケールは論点でないが、**パーサの対応文法範囲の拡張性**（新 CFN リソース型を足すコスト）は IR＋マッピング表の設計次第。§6[4] の「Terraform 出力など拡張の足場」という意図はあるが、拡張点の API は未定義。

### Q5. 内部矛盾・過少仕様の箇所

1. **リージョン情報の取得元が二重定義（内部矛盾の疑い）**:
   - §4.3 で `OBJECT-COMPUTER` = 主リージョン（`AWS-AP-NORTHEAST-1` → `ap-northeast-1`）と定義。
   - 一方 §4.5 / §5.4 では DB のレプリカ/witness を `WORKING-STORAGE` の `<ファイル名>-REGIONS` グループ（`REPLICA-1/2`, `WITNESS-REGION`）で指定。
   - サンプル `54-db.cbl` には **`CONFIGURATION SECTION` 自体が無い**（`OBJECT-COMPUTER` が無い）。では「主リージョン」はどこから来るのか？ `REPLICA-1`（東京）が主なのか、省略時デフォルトなのか、`-REGIONS` グループが `OBJECT-COMPUTER` を上書きするのか — **優先順位が未定義**。51-s3.cbl には `OBJECT-COMPUTER. AWS-AP-NORTHEAST-1.` があるのに 54-db.cbl には無い、という非対称が仕様の穴を露呈している。
2. **`FD` レコード項目と GSI/キーの対応が過少**: §4.5 は「`FD` のレコード項目 `PIC X`/`PIC 9` → 属性型 `S`/`N`（キー属性のみ定義に出す）」とする。54-db.cbl では `ORDER-ID`（RECORD KEY）、`ORDER-STATE`（ALTERNATE＝GSI）、`ORDER-AMOUNT`（非キー）がある。`ORDER-AMOUNT` は「キー属性のみ出す」なら AttributeDefinitions から除外されるはずだが、**DynamoDB では属性は動的なので整合はするものの、その意図が明記されていない**。また MRSC の `MultiRegionConsistency: STRONG` を出力に固定するのか、`DYNAMODB`（単一）と `DYNAMODB-MRSC` でどう分岐するかの Emitter 側ルールが未記述。
3. **デモ記述の語の揺れ**: §1 デモ山場②「東京・大阪＋witness のマルチリージョン強整合テーブル」と、§5.4 補足「`REPLICA-1/2` がレプリカ（東京・大阪）、`WITNESS-REGION` がソウル」は実質一致しているが、デモ文だけ読むと witness のリージョン（ソウル）が落ちている。審査員向けの表現として、witness が第 3 リージョン（ソウル）である点を明示したほうが MRSC の価値が伝わる（過少というより表現の最適化）。
4. **§4.6 の MVP 範囲の揺れ**: 「`compile`/`deploy`/`destroy` を必達」としつつ、§11 MVP では `CALL "DEPLOY"`/`"DESTROY"` は挙がるが CLI の `compile` が MVP の必達リストに明示されていない（ゴールデンテストが `compile` 前提なので実質必達のはず）。§4.6 と §11 で `compile` の MVP 位置づけを揃えるべき。
5. **Lambda の `Code` 欠落（Q3 再掲）**: サンプルが有効な CFN を生まないという点で、サンプルと「MVP でデプロイまでやる」という主張（§13 の実デプロイ、§12 W2）との間に未解消のギャップがある。

## 3. 良い点（維持すべき強み）

- **実機検証の裏取り**（§16）が企画書として破格に堅い。GnuCOBOL 3.2.0 実行確認、予約語 1006 語チェック、CFN MRSC の単一スタック表現確認は、審査でも「本当に動く」証拠として強い。

## 4. 改善提案（優先度付き）

### High（W1 のスペック化前に着手すべき）

- **H1. MVP 4 リソースの「COBOL→CFN 写像表」を §4 か §6 に追加する。** 各リソースについて「どの COBOL 項目（名前・レベル・VALUE）がどの CFN プロパティになるか」「必須だがサンプルに無いプロパティ（Lambda の `Code`/`Role`、IAM の `PolicyDocument`/`AssumeRolePolicyDocument`、S3 の `VersioningConfiguration`/`PublicAccessBlockConfiguration`）をどう補完/表現するか」を 1 行ずつ定義。これが無いと [3]Semantic と [5]Emitter が設計できない。
- **H2. リージョン決定ルールの一本化（内部矛盾の解消）。** `OBJECT-COMPUTER`（主リージョン）と `<ファイル>-REGIONS` グループ（レプリカ/witness）の優先順位・省略時デフォルトを明記し、`CONFIGURATION SECTION` が無い 54-db.cbl でも主リージョンが一意に決まるようにする。必要ならサンプルに `OBJECT-COMPUTER` を足すか、「DB の主リージョン＝`REPLICA-1`」と定義する。
- **H3. サンプルの CFN 妥当性に関する注記を追加。** 現サンプルは「COBOL として有効」の実証用であり、「そのまま有効な CFN になる」わけではない旨を明記し、MVP でデプロイ可能にするために各サンプルへ最低限必要なプロパティ（特に Lambda `Code`）の表現方法を決める。§12 W2 の実デプロイ目標と矛盾させない。

### Medium（W1〜W2 で詰める）

- **M1. デプロイ側エラー処理の設計。** ChangeSet 作成/実行失敗、スタック既存、ロールバック、認証失敗の分岐を §4.6 or §6[6] に追加（ABEND 演出は UI 層、失敗ハンドリングはロジック層として分離）。
- **M2. パーサの MVP 受理サブセットの明文化。** 継続行・ピリオド・複数 `MOVE`・添字範囲・`REF:` 循環などについて「受理/明示エラー」の線引きを §4 か §11 に表で。§13 の「パーサ沼」リスクの具体的な防波堤になる。
- **M3. ブラウザ内コンパイル→実デプロイの認証経路を設計。** デモ UI（§8）のクレデンシャル取り扱い（バックエンド署名？ 短期クレデンシャル？）を決め、鍵がブラウザに渡らない方式にする。Security CB の作風とも一致。
- **M4. ゴールデン期待値の初期作成フローを定義。** 期待 CFN を手書きするか、初回生成を人手レビューで確定するか（§9.2）。`UPDATE_GOLDEN=1` の運用とセットで。
- **M5. CLI `compile` の MVP 位置づけを §11 に明示。** ゴールデンテスト・CI が依存するため実質必達。§4.6 と §11 の記述を揃える。

### Low（余力・ストレッチ）

- **L1. 非ゴール節の新設。** 散在する非ゴール（jsii 非依存、`EXEC SQL` 不使用、Skeleton Crew 対象外、Emitter 自動生成は MVP 外、DSQL はストレッチ）を 1 節に集約し、審査員/読者が範囲を一読できるようにする。
- **L2. Emitter マッピングの自動生成案（§5 ⚠️）の MVP 外明記。** MVP は手書き表に倒す、と確定させて浮きを解消。
- **L3. デモ文の witness 表現の補強（§1 デモ②）。** witness が第 3 リージョン（ソウル）である点を 1 語添えると MRSC の価値が伝わる。
- **L4. `destroy` の対話プロンプトと CI 非対話 DESTROY の両立。** `--yes`/`--force` 相当の非対話フラグを CLI 仕様に足す（§4.6/§9.6）。

## 5. 結論

企画・審査対策ドキュメントとしては**提出に耐える完成度**で、特に実機検証と CDK 区別の論理は強い。実装着手（W1）に向けては、**トランスパイラの意味論（COBOL→CFN 写像表）の明文化（H1）**と**リージョン決定ルールの一本化（H2）**、そして**サンプルの CFN 妥当性の注記（H3）**の 3 点が最優先。これらは現状「規約で表す」という方針の下に暗黙化されており、スペック（§10）を書き始める前に 1 段階詳細化しておくと、W2 以降の実装とゴールデンテストが一気に進めやすくなる。審査基準 TBD（外部要因）以外の未確定は、いずれも自力で埋められる設計判断の範囲にある。
